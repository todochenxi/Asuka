## 项目关键架构结论（后续对话复用）

- 项目定位：**AgentOS — Enterprise Agent Harness & Runtime Platform**，本质是面向 AI Workload 的分布式操作系统。
- 一句话总纲：核心是统一的 **Execution Kernel**，上层负责 Goal→Decision→Action→Task，Kernel 负责 Scheduling/Lease/Retry/Checkpoint/Recovery/Cancellation，结果转 Observation 更新 State。Workflow/Skill/Tool/Multi-Agent/Evaluation 全部复用同一 Kernel。
- 核心协议循环：**G → D → A → T → E → O → S → D**（Goal/Decision/Action/Task/Execution/Observation/State）。
- 领域模型：Tenant → Agent → AgentVersion → AgentRun → RunAttempt → RunStep；Run 附属 Checkpoint / ContextSnapshot / Event。Retry = 新 Attempt，不是状态回退。
- 数据底座职责：PostgreSQL = Source of Truth（含 Outbox）；Redis = 运行时状态/锁/取消/幂等/限流；Kafka = Event Backbone；Qdrant = 向量；S3 = 大对象。采用 CQRS + Event-driven + Snapshot，不做纯 Event Sourcing。
- 路线图：M0 基础设施 → M1 领域模型 → M1.5 可靠性 → M2 Harness → M3 Runtime → M4 MCP/A2A → M5 RAG → M6 Model Gateway → M7 K8s → M8 Eval/Evolve → M9 多租户/治理 → M10 Execution Kernel → M11 Developer Platform → M12/M13 Cognitive → M14 Kernel Protocol → M15 落地代码。
- 设计纪律：每个模块先回答 6 问（为什么/负责什么/不负责什么/接口/数据流/故障），答完才允许 AI Coding；反对技术栈堆砌。

### 已收敛的关键定义（后续必须沿用）

**执行对象模型（P0 钉死）**
`AgentRun ⊃ Step → Task → Execution ⊃ Attempt`
- AgentRun = 业务级执行实例；Step = 逻辑执行节点（Execution Graph）
- Task = 可调度单元（**Scheduler 只认 Task**）；Execution = Kernel 生命周期实体；Attempt = 一次尝试
- 「Step vs Task」标准答案：**Step 是逻辑节点（做什么），Task 是调度单元（谁去跑）**
- 拆 **Business Execution**（AgentRun/WorkflowRun/SkillRun/EvaluationRun）vs **Kernel Execution**（ToolExecution/TaskExecution）。ToolExecution 不再与 Execution 并列，避免套娃

**三层职责（P0）**
- **Harness 控制 Agent**：Context/Policy/Memory/Guardrail/Cost/HITL
- **Runtime 驱动 Agent**：AgentLoop/Planner/DecisionEngine/ActionResolver/TaskFactory/ObservationProcessor（**移除 Scheduler/StateMachine/Retry/Cancellation/RunManager**）
- **Kernel 执行 Task**：StateMachine/Scheduler/Lease/Attempt/Checkpoint/Retry/Recovery/Cancellation/Idempotency
- **State Machine 是 Kernel 能力，不是 Agent 能力**

**数据表述（P0 修正）**
- ❌ "Kafka = Execution Truth" → ✅ **PG = Current Durable State / Business Source of Truth；Kafka = Durable Event Log**。一致性靠 Transactional Outbox + Idempotent Consumer

**状态机（P1）**
7 态：CREATED/QUEUED/RUNNING/**SUSPENDED**/COMPLETED/FAILED/CANCELLED
- SUSPENDED 带 `suspension_reason`：HUMAN_APPROVAL / CHILD_AGENT / TIMER / EXTERNAL_EVENT
- WAITING_HUMAN 不是生命周期状态，是 SuspensionReason；TIMEOUT 不是顶层状态（Attempt 层失败原因 → FAILED）

**Contracts（P1 重命名）**
不再叫"五大核心协议"，改 **Core Domain Contracts** 三组：
- Intelligence：Goal/State/Decision/Action/Observation/Plan
- Execution：Task/Execution/Attempt/Checkpoint/Lease/Cancellation
- Integration：Tool/Skill/Agent/Model/Event

**存储边界（P2）**
- 通用原则：PG=durable truth，Redis=runtime，Qdrant=**retrieval index**，Kafka=durable event log，S3=large object
- Qdrant **不是** Memory/Knowledge 的事实存储，可重建
- Knowledge 三层：S3(原始文档) → PG(metadata/version) → Qdrant(index)
- 新增 **Artifact**：Execution → Artifact → S3；Observation 只存引用

**其他**
- **Event ≠ Observation**：Observation 给 Agent 看，Event 给系统/审计/评估看。时间线 Event→Event→Event→Observation→StateChange
- **Actor + Mailbox 降级**为 Stateful Execution 的实现模型，不进第一版核心

### 第四轮：v2.0 → v2.1（第二轮评审，闭合概念）

评审判断：架构方向 9/10、领域边界 8.5/10、Kernel 设计 8/10、概念一致性 7.5/10。
v2.0 收敛的是**边界**，v2.1 闭合的是**概念**。13 项修正全部完成。

**P0**
1. **删除 `TaskExecution` / `ToolExecution` 领域对象** —— v2.0 把它们归为 Kernel Execution 又造成新套娃（会被追问"Execution 是抽象还是实体"）。Kernel 只有 `Task / Execution / Attempt`。唯一链路：`ToolCall → Action → Task(type=TOOL) → Execution → Attempt`。一个 Tool Call **产生 Task**，不直接产生 ToolExecution。
2. **AgentRun 与 Kernel Execution 边界** —— AgentRun 是业务语义 Run，**不等价于** Kernel Execution；其内部产生的 Task 由 Kernel 管理。否则 WorkflowRun/SkillRun/EvaluationRun 会再次出现"谁才是 Execution"。

**P1**
3. **Step → Task 改为一对多**（原一对一限制死了架构）。支持 Parallel / Planner / Multi-Agent / Fan-out / Fan-in。
4. **StateMachine 是通用 Mechanism**，分 AgentRun/Task/Execution/Attempt 状态机；第一版只实现 Execution + Attempt，AgentRun 状态由它们派生。
5. **Recovery 分两层**：Execution Recovery（Kernel，基础设施级，"怎么把 Execution 救回来"）vs Agent Recovery（Harness，改名 **`AgentRecoveryStrategy`**，策略级，"Agent 失败后下一步怎么办"）。消灭两个 RecoveryManager 撞车。
6. **Evaluation 提升为独立 Platform Domain**（原塞在 Harness 内）。Evaluator/Dataset/Experiment/Metrics/EvaluationRun；Harness 只调用。

**表述级**
7. SUSPENDED 补齐 **Wake-up 机制**（属 Kernel）：Suspended → Wait Condition → Event/Timer → Wake-up → Runnable Task → Scheduler。
8. Cancellation：Harness 可发起请求，**生命周期管理属 Kernel**。
9. Observation **不直接**更新 State，加 **State Reducer / State Transition** 层。
10. Confidence 改名 **`confidence_signal`**（不是 calibrated probability）；**禁止** `confidence > 0.9 → 自动执行`。
11. Checkpoint 明确恢复边界：current_step/completed_tasks/execution_state/**context_snapshot_id（引用不内嵌）**/variables/artifacts/recovery_metadata。
12. **M15 顺序修正**：Domain → StateMachine → Kernel → Repository Interfaces → PostgreSQL → Redis/Kafka（原来 Domain→PG→Kernel 违反自身原则）。
13. 新增 **§11.6 Future Extension**：SFT/DPO/RL、Tree Search/Self-Consistency、Actor/Saga/Workflow、Marketplace/GitOps 明确标注不在实现范围，防止范围失控被问穿。

### 第八轮：M15 阶段 3/4（Execution Kernel + Repository 接口）

产出 `packages/execution_kernel/`（8 个文件）+ `tests/unit/test_kernel.py`（15 用例）。
总测试 **81 个，全绿**：`python -m unittest discover -s tests/unit -t .`

**结构**
- `kernel.py` ExecutionKernel：submit（E-19 task 唯一索引）/ claim / heartbeat / complete / fail / suspend / wakeup / recover / request_cancel / cancel；内部维护 `_aggregates`（Attempt 内存态）与 `_tasks`（Scheduler 要 priority/tenant）
- `scheduler.py` Scheduler：priority + `-attempt_no`（重试让位）+ tenant round-robin fairness + WorkerCapability(executors/labels/free_slots) 匹配 → dispatch 时 Atomic Claim
- `recovery_controller.py` scan（过期 Lease → STALE）+ recover（新 Attempt + 新 fencing_token），`run_once()` 两步合一
- `wakeup_controller.py` `run_once(is_satisfied)`；内置 `timer_satisfied` / `approval_satisfied` 谓词
- `cancellation.py` CancellationService + CancellationToken（协作式取消；Redis 信号只是快路径，事实来源是 PG 的 `cancellation_requested`）
- `idempotency.py` IdempotencyGuard：同 key 只执行一次；异常时写 `__unknown__` 标记；`resolve_unknown(probe)` 回查；`assert_not_blind_retry(EXTERNAL_UNKNOWN)`
- `ports.py` / `inmemory.py` 接口与内存实现（SystemClock / ManualClock、InMemory* 、RecordingEventPublisher）

**踩坑（重要，后续别再犯）**

### 第十轮：M15 阶段 6（Redis）— 已完成

产出 `packages/execution_kernel/adapters/redis.py` + `tests/unit/{fake_redis.py,test_redis_adapter.py}`。
总测试 **129 个，全绿**（新增 20 个）。

**新增端口 `LeaseIndex`**（track/forget/due/clear）：ZSET(member=execution_id, score=expires_at)。
只回答"谁的 Lease 快到期了"，不回答"谁持有 Lease"——后者只有 PG 说了算，所以拿到 due 后仍回 PG 复核。
索引是 PG 的**派生视图**，方向只能 PG→Redis：`kernel._persist()` → `_sync_lease_index()`。

**Redis 三件套**
- `RedisLeaseIndex` ZADD 按 member 覆盖 → 续期天然幂等
- `RedisCancelSignalStore` SET EX ttl，只是通知
- `RedisIdempotencyStore` SET NX → 首次写入者胜；**get() 返回 None = UNKNOWN 不是"没执行过"**，必须回查绝不盲重试
- `rebuild_lease_index(index, repo)` 从 PG 重建

**关键设计决策（重要，别再踩）**
Recovery 只走索引的话 Redis 一挂就永远扫不到。直觉方案"索引空了就回落到 PG"是**错的**——正常空闲时索引本来就是空的，等于每轮全表扫，索引白建。
正解是**低频兜底**：`RecoveryController.sweep_every=10`，`scan()` 走索引、`sweep()` 直接扫 PG、`run_once()` 每 N 个周期额外 sweep 一次。
→ 原则：**Redis 全丢只允许造成"变慢"（晚 N 个周期发现），不允许造成"变错"（永远漏掉）。**

**测试替身**：`fake_redis.py` 只实现 7 条命令（SET NX/EX、GET、DEL、ZADD、ZRANGEBYSCORE、ZREM、FLUSHALL），TTL 惰性判定 + 时间可注入 → "过期"和"Redis 整个没了"都能确定性测试。

### 第十一轮：M15 阶段 7（Kafka + Worker）— 已完成

**投递语义 = 至少一次，所以去重是正确性的一部分**
`OutboxPublisher.drain()` 必须 **先 publish 后 mark_published**：崩溃在中间 → 重投。
反过来会丢事件（Read Model/审计永久缺一块且无从发现），比重复严重得多。
测试用 `CrashingPublisher`（投递成功但随后抛异常）复现：Kafka 收到 2 条，消费者处理 1 次。

**Kafka 三个硬点**
- `key = aggregate_type:aggregate_id` → 同聚合同分区保序（否则 completed 早于 running）
- `event_id` 必须在**消息体**里（header 转发/重放会丢）
- 批次末尾只 flush 一次（批次内 flush 破坏顺序）

**去重记录落在 PG 不是 Redis**（`processed_events` 表）：Redis 丢了会整批历史事件重跑。
→ 判据：**去重属于"正确性"，Lease 索引属于"快路径"**。同样一句"Redis 能不能丢"，答案相反。

**Worker 五件事**：回写带 fencing_token / 取消协作式 / 心跳(interval<ttl 构造时校验) / 失败转 FailureClass(EXTERNAL_UNKNOWN 不重试) / 丢 Lease 转 LOST_LEASE 绝不写结果。

**阶段 7 修掉的三个真缺口（都不是测试写错）**
1. **取消意图没人推进到终态**：`request_cancel()` 只写意图，PENDING 的 Execution 永远悬着。
   补 `CancellationService.sweep()`，规则：**只有持有有效 Lease 的 RUNNING 才等 Worker 协作，其余(PENDING/SUSPENDED/STALE/RUNNING+Lease过期)一律直接判死**。
2. **Scheduler 会把已请求取消的任务派发出去**（白占 Attempt，还会撞 E-17 把 Worker 打挂）→ `candidates()` 过滤 `cancellation_requested`。
3. **Worker 在 Lease 过期后崩溃**：`complete()` 抛 `LeaseRequired` 不是 `StaleWriteError`，没接住 → 两者都转 LOST_LEASE。

**踩坑**：sqlite `executescript` 才能跑多语句 DDL；shim 加了 `executescript` + `load_schema_sql(*names)`，
`connect(*extra_sql)` 支持追加 002 迁移。另给 `Connection.__del__` 兜底 close，消除跨模块 GC 的 ResourceWarning。

### 关键判断：两个洞其实是**一格**

- `SKILL_CALL` 与 `AGENT_DELEGATION` 语义相同：**派生一条子 Run**。
- 为什么不能走 `Executor.execute()`：一次 Execution 装不下子 Run 的 N 次 Execution

  Recovery 重放会把整条子 Run 的副作用再放一遍。
- 结论沿用 `ApprovalGateExecutor` 的先例：**Loop 拥有它**，在**派发之前、Harness 之后**
  接走（`_suspend_for_child`）。挂起顺序（submit → spawn → Checkpoint → claim
  → suspend → snapshot）与审批闸门逐条对齐，无一可交换。
- `SkillExecutor` / `AgentDelegationExecutor` 只做**诚实拒绝的安全网**：真被 Worker
  拿到，说明持有它的父 Loop 已经不在了。

## M29：X-3 事务边界 + 存储接线（v2.1.18，§67）

## M31：委派失败与取消的重试语义（空洞 218）→ v2.1.20

```

  → kernel.fail(TRANSIENT) → 父 Execution 回到 PENDING（attempt=2）
```

不是打转，是**换了主人**：从父 Loop 滑到 Worker，被一句"拥有你的 Loop 不在了"拒绝。

1. 真因被抹掉 —— 排障第一入口（父 Execution 的终态 error）读到的是 Worker 的拒绝，

## M33（空洞 221）：Run 级取消入口 —— v2.1.22

用户："继续"。按 M32 末尾自己的推荐做 221。

**洞的真实形状**：写 221 时以为它只是"测试不方便"。读完才发现：
一条 Run 在 AgentOS 里**根本不能被叫停**。取消只能从外部发生
（kill -9 / 手工改库 / 改策略再驳回），于是"停"的实现者是运维。
而 D-13 处理的局面（父已终态、子在跑）恰恰是取消缺位时**唯一**会发生的局面 ——
一个洞是另一个机制唯一的应用场景，这件事本身就是答案。

**新不变量**
- **B-8**：`AgentLoop.cancel(reason=, by=)`，`reason` 与 `by` **都必填**
  （A-8 同款：匿名取消进不了审计）。取消**不是** `step()` 的分支 ——
  走 `step()` 要经过 Decision→Policy→Action，而被 Policy 拦住的 Run 会永远取消不掉。
- **B-9**：取消级联到在等的子 Run，**先子后父**，且叫停后必须 `mark_delivered`。
  - 先子后父的理由：反过来崩一次留下"父已终态、子在跑" = D-13 那种必须有人看的残局；
    先子后父留下"父还活着、子已取消" = 父被正常唤醒走 D-12，不需要人判断。
  - **第三半（本轮实测才量出来的慢泄漏）**：不 `mark_delivered` 的话，
    子 Run 已终态未交付 ⟹ 永远留在 `undelivered()` ⟹ sweep 每轮捞它一次
    ⟹ 父已终态 ⟹ 每轮记一条 D-13 孤儿。取消越多 sweep 越慢。
  - `cancel_child` 写进 `ChildRunSpawner` **端口**（不是 getattr 碰运气），
    碰不到就抛 —— PR-26 同款。
- **B-10**：终态不可取消（B-3 另一半）；**取消之后必须落终态快照**（R-1）。
  少了后者，取消只改内存：重启恢复出一条 RUNNING 的 Run，取消等于没发生。

**实现落点**
- `loop.py`：`cancel()` / `_cancel_pending_child()` / `_cancel_gate()`；
  `StepOutcome.CANCELLED`；用 `kernel.cancel()` **不是** `kernel.fail()`
  （那一步没失败，只是不必再发生；判 FAILED 会让人去找"为什么失败" = PR-19）。
- `delegation.py`：`ChildRunSpawner.cancel_child()` +
  `InProcessChildRunSpawner.cancel_child()`（进程内递归调子 Run 自己的 `cancel()`，

## M34（空洞 222）：跨进程取消的通道 —— Run 级取消意图

**起因**：§71 登记的 222。真形状不是"少了个通知"，是**系统里同时存在两条
互相矛盾的事实** —— 父侧"结果我不要了"（登记处 cancelled），子侧"我还活着"。
用户按的是"停止"，得到的是**停止了一半**。"停一半"比"不停"更难发现：
页面显示已取消（不报错），账单还在花钱（也不报错）。

**为什么 Kernel 现有取消补不上**：它挂的是 **Execution**。一条子 Run 有自己
一堆 Execution，且它在等孙 Run 时**手上根本没有活的 Execution** —— 那条
SUSPENDED 的 Execution 是"它在等"的证据，不是"它在跑"的证据。粒度不同。

**三段式**（与 Kernel 同构）：
- Durable Intent：`011_run_cancellations.sql` + `PostgresRunCancellationStore`
- Safe Point：`AgentLoop._step()` 顶部（`_pending_cancellation()` → 自己 `cancel()`）
- Sweeper：`RunCancellationService.sweep()` + `apps/run_cancellation_sweeper`

**落点**（都在这一次改完）：
- `packages/agent_runtime/cancellation.py`（RunCancellation / Store / Service）
- `loop.py`：新字段 `cancellations`；`cancel()` 里 `_request_cancellation()` 在
  `_cancel_pending_child()` **之前**（R-7），末尾 `_settle_cancellation()`（R-8）；
  `_cancel_pending_child()` 给**子 Run** 也写意图（级联版 R-7）；
  `run()` 的停止集合加 `StepOutcome.CANCELLED`
- `assembly.py`：`cancellations` 参数，刻意**不给内存兜底**（给了 = 两个进程各一份）
- `apps/_bootstrap.py`：`_REQUIRED_EXTRAS["cancellations"]`（收不下就装载失败）、
  `build_run_cancellation_sweeper`、control_plane / child_run_consumer 都接上
- `agent_api`：`RunView.cancel_requested` 新字段；
  `cancel_run` 装载不了时落意图而不是 404；`_try_stack()` 抽出（三种"装载不了"
  含义不同，判据交给调用方）
- `examples/demo_stack.py`：两个 factory 都要收 `cancellations`
- 控制台：`cancel_requested` 时显示"已请求叫停 —— 它现在**还没停**"

**⚠️ 本轮最大的收获：R-10 被自己推翻**
第一版 `sweep()` 写的是 `except LookupError: settle()` —— 把"没有快照"读成了
"这条 Run 不存在"。错。快照只在**挂起**时拍（R-1），一条正在跑、从没挂起过的
Run 也没有快照 —— 它活得好好的。在那里结掉意图 = 写下"我取消了它"而它还在跑
（PR-19），而且从此**再没有人**会去叫停它（意图已不在 pending）。
改成"什么都不做、继续 pending"：代价是永远没人认领的意图一直留在索引里
（变慢且看得见），按 A-12 比"变错且没人知道"好。
> **"读不出来"不等于"它没了"。**

**变红验证**：安全点 → 3 红；级联写意图 → 3 红；run() 不停在 CANCELLED → 1 红；
