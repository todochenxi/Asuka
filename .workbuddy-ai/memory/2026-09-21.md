## M37 · 空洞 226：等到什么时候为止（基线 → v2.1.26）

**起因**：M35 登记的 226 只说了半张脸 —— "请求永久 pending、孤儿永不登记"。
真正要命的那半是 `pending()` **同时有 `ORDER BY requested_at` 和 `LIMIT %s`**：
僵尸意图的 `requested_at` 最老，所以它**永久占据队首 1 号位**，每 tick 被捞起、
`continue`、放回。攒够 64 条僵尸之后，**新的取消请求永远进不了扫描窗口**，
而 `sweep()` 每 tick 返回 0 —— 界面显示"没有待处理取消"，
跨进程取消通道其实已经停止服务。按 A-12 这不是"变慢"是**变错**；
按 012 的脸谱它是**脸 B**（连响都不响）。

M34 的 R-10 判过一次僵尸意图，结论是"变慢且看得见，比变错且没人知道好"——
那条判断对**一条**僵尸成立，但它没有看 `LIMIT`。

**为什么只有"等待上限"、没有"死亡检测器"**：系统里唯一带活性的东西是 Kernel 租约，
而 `LEASE_EXPIRED` 是**可重试**的，意思是"驱动者换了、另一个 worker 接手"，
不是"这条 Run 没了"。拿它当死亡证明，会杀掉一条正被 Recovery 救活的 Run。
Run 没有心跳列，快照只在挂起时落（R-1），跑着的 Run 什么都不往 PG 写。
所以：**没有死亡检测器，只有等待上限** —— 前提是到点后的动作必须诚实地记成"我们不知道"。

**新增不变量**
- R-11：每条取消意图都带等待上限 `abandon_after`，**在 request 那一刻固化**；
  到点放弃。放弃 = "**我们不知道**它停没停"，**不写终态、不写 `settled_at`**
- R-12：放弃一条子 Run 的等待时，若父已终态，必须补记 D-13 孤儿，
  理由**点名"结局未知"**（字面写 `WE DO NOT KNOW`），不得冒充"已取消"。
  缺 `child_registry` / `saga` 要**抛**，不静默跳过
- R-13：放弃过的意图必须**退出 pending 队列** —— 唯一落点是**部分索引的谓词**
  （`WHERE settled_at IS NULL AND abandoned_at IS NULL`），Python 过滤不算
- R-14：放弃**不是撤回**。那条 Run 后来撞上安全点仍应停下来；
  `settled_at` 与 `abandoned_at` 允许**同时**有值（所以不加互斥 CHECK）
- 三列回答三个不同问题（B-7）：`settled_at` 事实 / `abandon_after` 策略 /
  `abandoned_at` 决定

**改动**

## M44 / 空洞 223 —— 叫停也要幂等键（v2.1.33）

**洞的形状**：A-3 要"`POST /runs` 幂等"，M36 做成了真的（`run:<key>` 落 PG）。
但 `POST /runs/{id}/cancel` 是同一条规矩下的另一个写操作，它没有键 ——
于是"t1 真的停了（200）→ t2 网络抖 → t3 重试"拿到的是 **409 RUN_TERMINAL**。

关键：**409 没有撒谎**（确实是终态），错在**它是个错误码** ——
一次成功的叫停被报成了失败；且 409 分不出"被你叫停的"和"它自己跑完了"，
客户端要么骗人要么猜。

**新判据**

    D-35  取消是写操作，所以它也吃幂等键 —— 重试拿到**第一次的答案**，
          不是拿到一个 409 去猜
    D-36  幂等记录里存的是**答案**，不是一个指向活对象的指针

D-36 与 `start_run` **方向相反**，这不是矛盾是保护的东西不同：
- `start_run` 存指针，装载不回来 ⟹ 宁可喊 `RUN_NOT_RELOADABLE`（不许多出第二个 Run）
- `cancel_run` 存答案，装载不回来 ⟹ 照样给（不许把已发生的叫停报成失败）

原因：取消的答案里最要紧的一半（`status="unknown"` / `cancel_requested=True`）
恰恰**装载不回来** —— 跨进程那条路只写进了一张取消意图表。
探针实录到库里存的那份答案 `{'status': 'unknown', 'cancel_requested': True}`。

**另外三条实现约束**
1. 命名空间 `run:` / `cancel:` 必须分开 —— 共用的后果是取消**静默撞上**建 Run 的记录，
   于是这次叫停根本没发生而客户端拿到 200（"看起来成功实际没做"）。
2. 指纹用 `sha256(json.dumps(sort_keys=True))`。**内置 `hash()` 不能用**：
   str 的 hash 带随机盐（PYTHONHASHSEED）⟹ 重启后指纹对不上 ⟹ 假 422，
   而单测跑在同一进程里**全绿**。守卫：起两个种子不同的子进程比指纹。
3. 失败不占键（`put` 只在工作真的写完之后）。

**顺手补的**：`start_run` 原本缺键复用校验（同一键换 `user_request` 会静默拿回旧 Run）；
`RunView.from_dict()` / `ApprovalView.from_dict()` 是 `to_dict()` 的反面。

**两个自己踩的坑（值得记住）**
1. 变红第 12 组最初用文本扫描 `assertIn("Idempotency-Key", body)`，而 `_cancel_run`
   的 **docstring 里就写着这四个字** —— 删掉真实参数照样绿（PR-22：docstring 不算调用）。
   改成 AST 扫描（剥 docstring）。
2. AST 扫描自己的坑：**形参默认值不在 `fn.body` 里**。
   `idempotency_key: str = fastapi.Header(default="", alias="Idempotency-Key")` 挂在
   `fn.args.defaults` 上。只扫 body 会把真读了 header 的路由判成"没读"
   （扫出来只有 `{'agent_id'}`）。补：连 signature defaults 一起扫 + 控制组。

**测试数**：1022 → **1050** 单元（新增 28）；147 → **152** 集成（新增 5）；合计 1169 → **1202**。
变红验证 13/13（含 durable=FALSE 那条走集成层真 PG）。`red44.py` / `probe44.py` 已删。

**冻结**：基线 → `AgentOS_企业级Agent平台架构_v2.1.33_最终冻结版.md`（新增 §82、M44 里程碑行、
版本段 v2.1.33、11 处 223 行改"本轮闭合"）；`apps/api/app.py` → 2.1.33（PR-24）。
一句话：**"如实报错，不等于把事情说对了。"**
另一句：**同一条规矩不许有两个实现 —— 但允许有两个方向（B-7 说的是"一个事实一个定义"，
判据是"它保护的东西是不是同一件"，不是"写法一样"）。**

## M46 / B-4 违反：驳回后 Run 停在 suspended 但无 waiting_for（v2.1.35）

**洞的形状**：`loop.reject()` 的流程是 `_close_gate` → `_clear_pending` → `_record(DENIED)`。
`_close_gate` 已经把 Execution 从 SUSPENDED 走完到 COMPLETED，但**没有调 `_sync_after_execution()`**
—— Step.status 仍然是 SUSPENDED（没人重新投影），Run.status 仍然是 SUSPENDED。
而 `pending_approval` 已经是 None 了：Run 说"我在等"，但说不出在等谁（B-4 违反）。
`expire_approvals()` 有同样的病。

**不只是界面骗人**：如果在"假挂起"窗口里拍快照（后台进程的 `capture()`），
会撞上 R-1/R-6 的 InvariantViolation（SUSPENDED 但没有 `pending_*_id`）——
快照落不下来。

**新增不变量 B-11**（B-4 的操作细则）：关掉闸门后必须**立刻**重新派生 Step/Run 状态。
"立刻" = 在同一个方法里，不依赖调用方记得再调一次。

**改动**：`reject()` 和 `expire_approvals()` 的 `_clear_pending()` 之后加 `_sync_after_execution()`。

**变红验证**：去掉 reject 里的 `_sync_after_execution()` → 3 fail + 1 error；
5/5 绿（含快照一致性测试）；1052 全量绿（1047 → 1052）。

**冻结**：v2.1.35 + §84；`apps/api/app.py` → 2.1.35。
一句话：**"关掉了闸门，就要把状态一起带走 —— '关了'不等于'走了'。"**
另一句：**B-4 说"SUSPENDED 必须说清楚在等什么"；
B-11 补的是"不说在等什么的时候，就别让它停在 SUSPENDED"。两者是一条规矩的两半。**

## M48 · 空洞 228（真形状）：Execution 级取消跳过意图直接判死（v2.1.37）

## M51 · B-3 该报 409 而不是 422（v2.1.40）

**怎么撞到的**：并发探测（同一条 Run 同时发 6 个 drive）。
```
单线程：Run 已 completed → 再 drive → 409 RUN_TERMINAL
并发  ：一个先跑完，另一个推到一半才发现已终态 → 422 INVARIANT_VIOLATION
```
**同一个事实两个状态码** —— 调用方得靠错误消息里的 "B-3" 字样才能判断，脆弱。

**根因**：B-3「终态不可变」用 `InvariantViolation` 抛（run.py:136），
而 `agent_api/errors.py` 映射表规定：
- `IllegalTransition` → **409**（资源存在、状态明确，只是转换不允许）
- `InvariantViolation` → **422**（请求本身不合法，改请求就有用）

B-3 属前者。报 422 等于告诉调用方"改改请求"，而它改一万次都一样。

**修法**：只改异常类型（`InvariantViolation` → `IllegalTransition`），**消息一句没动**。

**真跑过**（并发 6 个 drive）：修复前 `{200:4, 422:2}` → 修复后 `{200:4, 409:2}`，422 消失。

**已知边界**：状态码统一了，但错误码字符串仍有两种
（单线程 `RUN_TERMINAL` / 并发 `ILLEGAL_TRANSITION`）。
都是 409 冲突类，按状态码分支够用。不强行合并 ——
"入口就发现终态"与"推到一半才发现"**起因不同**，合并会丢掉这个区别。

**变红验证**：改回 InvariantViolation → 红 3 条 ✅。
顺带更新了 `test_business.py::test_b3_terminal_is_immutable`（原断言 InvariantViolation）。

**测试**：单元 1085 → **1088**（+3）。

**教训**：**并发是把"看起来没问题"的设计打出原形的那盏灯** ——
单线程下一切自洽，两条路同时走就露馅了。以后改状态机相关的东西要跑并发探测。

## M66 · 取消事件真库验证 + 修掉一个 PG/内存行为不一致（v2.1.55）

**起点**：M47 的三个事件只有内存单测 → 补真库验证（outbox 三条 + payload 归因 + 另一条连接可读）。

**⭐ 补的时候抓到一个真 bug**：PG 版 `request()` **无条件发事件**。
但意图已 settled/abandoned 时，INSERT 的 `WHERE settled_at IS NULL AND abandoned_at IS NULL`
不满足 → **那一行根本没改动**（rowcount=0），事件却发了 → 审计流多一条假的"又要求取消了一次"。
**内存版这种情况是不发的**（M47 单测守着）。
修法：`rowcount == 1` 才发。

**为什么重要**：一个 store 两种实现（内存给单测、PG 给生产）是常态。
**只有一种实现里成立的保证，等于在生产上不成立**，而单测全绿会让人以为成立。
这正是"只用替身验过"的代价 —— 也是补真库测试的价值（这一轮就是活例子）。

**顺带学到两条真实行为**（我最初的期望写错了）：
- 已 settled 的意图**不会** abandoned（R-8/R-11 不复活）→ 按结局二选一，不是三条齐全
- 已结掉的意图再 request：不复活，也不发事件

**变红验证**：去掉 rowcount 判断 → 红 1 条 ✅。

**测试**：集成 188 → **194**（+6）。单元 1154。服务 v2.1.55。

**本轮定下的操作规范（已验证有效）**：改版本号（mv 文档 + 改 app.py）必须**在跑测试之前**
连着做完。改完再跑 → 0 红条；边跑边改 → 版本断言红（那个挂很久的"偶发红"就是这么来的）。

**顺带做了一次同类审计（结论：干净）**：修完 request 后，把**所有事件发射点**都查了一遍
守卫情况 —— 取消 settle/abandon 有 `if ok`，补偿 claim 有 `rowcount==0 → return None`，
补偿 save 有 `rowcount==0 → raise` + `if before`，upgrade/amend_reason 都有。
**"无条件发事件"这一类 bug 全仓只有 request 一处，已修。** 变红验证也确认它不会悄悄回来。
