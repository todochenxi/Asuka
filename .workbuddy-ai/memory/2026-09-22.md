## Temporal 调研（对项目定位有战略影响）

**核心机制**：Workflow（确定性编排代码）+ Activity（副作用，自动重试）+ Event History（唯一事实源）+ Replay（Worker 恢复时重放历史重建状态）。状态不落业务库，靠重放事件历史恢复到断点。

**⚠️ 重大变化：Temporal 已于 2026 年 5 月 Replay 2026 正式转向 AI Agent**。定位从"持久化工作流引擎"改为"构建可靠 AI Agent 的生产级运行时"。已发布：
- OpenAI Agents SDK 集成（GA，含 sandbox）
- Google ADK 集成（LLM 调用与工具执行以 Activity 运行）
- Workflow Streams（基于 Signal/Update 的持久化流式，支持 token 批次与护栏）
- External Payload Storage（大 payload 落 S3，Public Preview）
- Standalone Activities（Activity 可独立运行，Public Preview）
- Serverless Workers（AWS Lambda，Pre-release）
- Task Queue Priority & Fairness（GA）、Nexus、多区域复制 RTO 20 分钟
- 获 AWS AI Competency（Agentic AI 类别）

**与本项目 Kernel 的逐项对照**（几乎全覆盖）：
| AgentOS 组件 | Temporal 对应 |
|---|---|
| ExecutionStateMachine | Workflow 代码本身即状态机 |
| Scheduler + Priority + Aging + 租户公平 | Task Queue Priority & Fairness（GA） |
| Lease + heartbeat | Activity heartbeat + timeout |
| Attempt + RetryPolicy | Activity Attempt + RetryPolicy |
| Checkpoint | Event History 自动，无需手写 |
| recovery_controller | Replay 自动恢复，无此组件 |
| wakeup_controller | Signal + Timer（可等数月） |

**Temporal 明确不做**（本项目的真实空间）：Agent 语义（Goal/State/Decision/Action/Observation）、Model Gateway 与模型路由、成本治理、Context 工程与 Memory 分层、RAG、护栏引擎、评估与失败归因、Step→Task→Execution→Attempt 这套 Agent 特有执行对象模型。

## M77 · 带着没被处理的失败，不许宣布完成（v2.1.65）

**探针实录（起因）**：
```
step 1  工具不存在 → StepOutcome.FAILED   agent_run running
step 2  脚本用完 → FINISH                 agent_run **completed**
```
而失败证据就在 `state.variables["result:exec_…"]` 里（`kind: execution_failed`），没人看。
**一个关键步骤失败了的 Run 被宣布 COMPLETED。**

**为什么是"说谎"不是"少功能"**：引擎看不见失败（按脚本走），
但**宣布终态的是 Runtime**（B-7）—— 谁宣布谁负责核实。

**新增 I-11**：完成前必须没有"**自上次规划以来**未被处理的失败"，有则 REPLAN。
判据钉在 **Loop 的 FINISH 分支**，不钉在引擎（换一个笨引擎谎言就回来了）。

**两个设计决定**（各有一条变红守着）：
- **按"上次规划"划界，不是数全部失败**：否则"第一步失败、换计划后成功"的 Run
  永远无法完成 —— 等于把可救的失败也判死刑。REPLAN 的语义就是"这份计划行不通"。
- **从 `state.observations` 推，不用计数器**：计数器在快照重载/进程重启时会丢，
  于是"有没有失败过"在重启前后给出不同答案。

**⭐ 它给 M76 修好的 REPLAN 边带来了第一个真正的触发条件** ——
M76 只是把边修通（通了、有界了），M77 才让它真的会被走。
两轮合起来：M76 修边 + M77 给触发条件，I-10 保证不空转（救不回来 → FAILED，
唯一不会变成的状态是 `completed`）。

**测试** 5 条（含两个控制组）。变红 2/2。单元 1233 / 集成 201 全绿。

**写测试踩到的**：`_loop_with_bad_tool` 放在第一个 TestCase 里，
第二个 class 用不到 → 直接内联构造 loop（别为了复用把 helper 挂到基类上）。

## M78 · 重规划必须真的换一份计划（v2.1.66）—— 补的是 M77 自己留下的洞

**探针**：M77 之后问"重规划换来的计划长什么样"：
```
#0: plan_id=plan_53a5…  shape=(('n0','step-0','task'), ('n1','step-1','task'))
#1: plan_id=plan_7bd2…  shape=(('n0','step-0','task'), ('n1','step-1','task'))
形状一样吗： True
```
`plan_id` 每次 `new_id()` → **从对象上看每次都"换了计划"**，但节点一个没变。

**⭐ 它把上一轮的 I-11 洗白了**（本轮最要紧）：
```
step 1  坏工具 → FAILED
step 2  I-11 拦下 FINISH → REPLANNED
step 3  重规划（形状相同）→ FINISH → **completed**
```
I-11 只看"上次规划以来"，重规划一次计数归零 →
**一个失败过的 Run 多花一轮重规划就又"成功"了**。

**新增 I-12**：换不出**形状不同**的计划 → 判 FAILED。
比形状不比对象（`plan_id` 必然不同，比对象 = 宣布"每次都换了"）。

## M79 · 终态必须带上原因（v2.1.67）

# M85（v2.1.73）· "只能由工厂构造"不是约束，是注释

## 洞的形状（§0.6 找洞法：grep 承诺句）

`observation.py` 里 I-6 那条唯一入口的 docstring 写着：

> "I-6：来自执行的 Observation 只能由这个工厂构造，必须绑定真实 Execution。"

但 `Observation` 是 `@dataclass(frozen=True)` —— **`__init__` 是公开的**。
`frozen=True` 只保证**不可变**，不保证**构造受控**。
更刺眼的是：`execution_id: str | None = None` 那个**默认值本身就是漏洞的形状**。

**把锁挂在门上，却没有门框。**

## 探针（`probe84.py`）四扇门全开

| 撞法 | 结果 |
|---|---|
| 直构 `EXECUTION_RESULT` 不带 `execution_id` | 成功 |
| `execution_id=""`（空串，同样没绑定） | 成功 |
| 非执行来源挂 `execution_id="exec_FAKE"` | 成功 |
| `attempt_no=0 / -1` | 成功（**工厂拦得住，`__init__` 拦不住**）|

## 危害：账本可解释性

- 一条声称"我来自某次执行"的 Observation **可以完全没有 execution_id**
  → 问不出"它有没有实证"
- 一条 `human_input` 可以顺手挂 `execution_id`
  → **"有 execution_id"不再能推出"它真的来自执行"**

而 reducer / 审计查询**正是靠这个字段分流**。
⇒ **一个失去意义的信号，比没有信号更坏。**

## 修法：判据搬进 `__post_init__`（所有路径的汇合处）

```python
def _assert_source_matches_binding(self) -> None:
    source_is_execution = self.source is ObservationSource.EXECUTION_RESULT
    if source_is_execution:
        if not self.execution_id:        # ← 空串与 None 同罪，不能写 is None
            raise InvariantViolation("I-6: ... requires a non-empty execution_id")
        if self.attempt_no is None or self.attempt_no < 1:
            raise InvariantViolation("I-6: ... requires attempt_no >= 1")
    elif self.execution_id is not None:
        raise InvariantViolation("I-6: only source=EXECUTION_RESULT may carry an execution_id")
```

**双向**是刻意的（前两扇门 + 第三扇门是两个方向的问题）。
**刻意留的口**：`attempt_no` 对非执行来源仍可选 —— 有控制组测试守着。

为什么不只写在 `from_execution_result` 里？
**绕过工厂的人当然不会走工厂。** 判据必须住在**每一条构造路径都经过**的地方
（工厂 / 直构 / 快照恢复，`__post_init__` 是三者唯一的汇合处）。

## ⭐⭐ 本轮最值钱的错误：变红验证 M2 第一版是**假绿**

M2 变异 = 把 `if not self.execution_id:` 改成 `if self.execution_id is None:`（放空串过去）。
预期：空串测试该红。**结果：照样绿。**

根因：那条空串测试是 `self._raw(execution_id="")`，**没带 `attempt_no`**。
空串绕过 id 检查后，**撞上了 `attempt_no is None` 那道** —— 照样抛、照样绿。

**我验证的是"某处会拦"，不是"这一处会拦"。**

修法：`attempt_no=1` **给足** + 断言拒绝理由**点名** `execution_id`：

```python
with self.assertRaises(InvariantViolation) as ctx:
    self._raw(execution_id="", attempt_no=1)
self.assertIn("execution_id", str(ctx.exception))
```

⇒ **通则：断言里除了"被测的那一项"，其他字段一律给足。**
否则多道校验叠在一起时，一个照样绿、一个必红，而两者在变异面前表现完全不同。

⚠️ 这与 §119.5（M82 变红 M4 没红）**同一族错，我栽了第二次**。
M82 那次是"把存在当成了被处理"，这次是"把某处会拦当成了这处会拦"——
都是**断言的边界没划在守点上**。

    "Planner 的 Plan Validator 会检查 DAG 环；这里做领域级兜底。"

—— **全仓没有 Plan Validator**。更要紧的是那段时间里 `depends_on`
**根本没被执行过**，因为 `_ensure_step()` 按下标取：

    node = plan.nodes[len(self.steps_of_run)]

两张脸，同一个根因 —— **计划按位置消费，不按意义消费**：

  ① 计划说 `n2 depends_on n1`，n2 排在前面 → 运行时**先跑了 n2**。
  ② `len(steps_of_run)` 是"这条 Run 跑了多少步"，**不是**"这份计划
     消费到第几个节点" → **重规划换出的新计划，前 N 个节点被静默跳过**。
     实录：`['a0', 'a1', 'b2', 'ad-hoc-3']` —— b0/b1 从来没被执行过。

## 新增两条不变量

| 不变量 | 内容 |
|---|---|
| **I-16** | 节点进 Step 的依据是"**它准备好了**"，不是"**下标轮到它了**"。依赖已**完成**（只认 COMPLETED，FAILED 不算）且没做过。游标属于**这份计划**，不属于这条 Run。 |
| **I-17** | `run()` 的停止条件是"**这条 Run** 到了终态"，不是"这一步的结果属于某张枚举表"。 |

**I-17 是 I-16 逼出来的**：I-16 新增了一条"卡住 → REPLAN → 换不出 → FAILED"
的路径，而 `run()` 的白名单里**没有 FAILED**（那是对的：FAILED 作为
"这一步的结果"通常不是终点），于是 `steps` 不再增长 → `steps >= budget`
永远不成立 → **`run()` 永远转下去**。L-7 写下的正是这句话。

★ 处置：**不把 FAILED 塞进白名单**（那会把"某一步失败"也当终点，
弄坏 I-11 的换计划路径），而是补上第二条停止条件。

# M87 · 计划必须按「意义」消费，不是按「位置」消费（v2.1.75）

## 洞是怎么找到的 —— §0.6 承诺句 grep

grep 代码里的绝对承诺句，命中 `plan.py` 的：

    "Planner 的 Plan Validator 会检查 DAG 环；这里做领域级兜底。"

—— 而**全仓没有 Plan Validator**（只命中 `Execution.validate()`，与 Plan 无关）。
顺着往下查 `depends_on`，发现它被校验（完整拓扑排序）、被持久化（快照），
**却从来没被运行时读过**。

## 两张脸，一个根因

    `_ensure_step()`:  node = plan.nodes[len(self.steps_of_run)]

**一、依赖图只被校验，从没被执行。**
一份合法但顺序颠倒的计划（`n2 depends_on n1` 却排在前面）→ 运行时**先跑 n2**。

**二、游标属于 Run，不属于计划。**
`len(steps_of_run)` 是"这条 Run 跑了多少步"，不是"这份计划做到第几个节点"。
重规划换出新计划后从 `plan.nodes[已跑步数]` 开始取 →
**新计划的前 N 个节点被静默跳过**。探针实录：

    plan A = [a0, a1]  →  重规划  →  plan B = [b0, b1, b2]
    实际实例化顺序 : ['a0', 'a1', 'b2', 'ad-hoc-3']

b0 与 b1 从来没被执行过。**系统在"换一条路"，换来的路的头两步被跳过了。**

## 用户做的两次决策

1. **依赖图怎么治** → 选「**让依赖图变成真约束**」（而不是删掉字段、
   也不是只让它"响"）。
2. **计划卡住时怎么办** → 选「**不编造：不实例化，走 REPLAN**」
   （而不是退回 ad-hoc 步）。

## 新增 I-16 / I-17

- **I-16**：节点进 Step 的依据是"**它准备好了**"（依赖都已完成 + 没做过），
  不是"下标轮到它了"。计划**卡住**（还有节点没做但一个就绪的都没有）→
  **不编造 ad-hoc 步**，走 REPLAN。与"**用完**"（常态，允许 ad-hoc）必须分得开。
- **I-17**：`run()` 的停止条件是"**这条 Run** 到了终态"，不是"这一步的结果
  属于某张枚举表"。两张表说的是两件事。

## ⭐ 1319 条既有测试一条不红

这不是"改得干净"，是**这条保证此前一直没被守过**。既有测试的计划要么没有依赖
（`ScriptedPlanner` 给 `n0, n1, …`），要么依赖恰好与顺序一致
（`test_agent_loop_full` 给 `n1, n2(dep n1)`）—— 两种取法给出同一个答案。
与 M85（1287 条全绿）同款。

⇒ 通则：**补判据时，要专门写一条"让两种取法给出不同答案"的用例。**

## ⭐ 第二个洞是变红验证顺手撞出来的（I-17）

`run()` 的停止条件是一张 `StepOutcome` 白名单，**没有 FAILED**。
作为"这一步的结果"它确实不该有（失败是事实，Agent 要据此换计划 I-11）。
但"这一步怎么了"与"这条 Run 还在不在"是**两个事实**：

    重规划换不出形状不同的计划 -> `_plan()` 返回 False
    -> `_declare_terminal(FAILED)` -> step() 从此每次都返回 FAILED
    -> steps 不再增长 -> steps >= budget 永远不成立 -> **run() 永远转下去**

没有报错，也没有尽头。L-7 自己写过这句话，它把 `DENY_LOOP` 加进了那张表 ——
**看见了症状，没看见判据选错了对象。**

## ⚠️⚠️ 一次流程事故：工具自己把世界改坏了（这轮最贵的教训）

变红脚本会真的改源文件，还原写在 `try/finally` 里。跑到 M4 时我**中途 kill** 它
→ `finally` 没执行 → **变异留在 `loop.py` 里**。连锁反应：

1. 跑全套 → 89 errors，看起来像"我的改动弄红了既有测试"
2. 把 loop.py 拷成备份 —— 那份备份是在**污染之后**拷的，装着变异
3. 用 `git checkout HEAD` 验证"HEAD 是绿的" → 判断对，**结论错**：红的是变异
4. 从备份恢复 → 把变异又装了回去

三条纪律：
- **原文件先落盘一份** + 给子进程加 `timeout=`；`finally` 里比对并回报残留
- **备份要在确认干净之后才拷** —— 顺序错了，备份就是污染的传播器
- **看到"既有测试红了"，先问：磁盘上的代码真是我以为的那份吗？**
  最便宜的验证：grep 变异串本身

顺带：**Python 重定向 stdout 是带缓冲的**（日志空着 ≠ 没在跑），用 `-u`。
