2 · 执行对象模型（P0 已钉死）

AgentRun          ← 业务语义上的 Run（≠ Kernel Execution）
    │ contains
    ↓
   Step            ← 逻辑执行节点
    │ produces (一对多)
    ↓
 Task ─ Task ─ Task ← 可调度工作单元（Scheduler 只认 Task）
    │ scheduled as
    ↓
 Execution         ← Kernel 生命周期实体
    │ retried as
    ↓
  Attempt          ← 一次具体尝试
对象定义例子
AgentRun业务级 Agent 执行实例 —— 用户让某个 Agent 完成一次任务Run #10086："帮我分析 Q3 财务风险"
StepAgent / Workflow 的逻辑执行节点，属于 Execution GraphStep：research_company
Task可调度的工作单元。Scheduler 只认识 Task。一个 Step 可产出多个search_official_site / search_news / query_db
ExecutionTask 在 Kernel 中的生命周期实体：状态 / Lease / Checkpoint / Cancel / Retry / RecoveryExecution #100
AttemptExecution 的一次具体尝试Attempt #1 → timeout；Attempt #2 → success
面试官问："Step 和 Task 有什么区别？"
Step 是逻辑节点（做什么），Task 是调度单元（谁去跑）。 Step 描述"这一步要调研这家公司"，Runtime 为它生成一个或多个 Task；Task 进入 Kernel 才获得 Execution 生命周期。 Step 属于业务语义层，Task / Execution / Attempt 属于 Kernel 层。

Step → Task 是一对多（v2.1 修正）

Step: research_company
   ↓  Planner / Fan-out
Task 1: search_official_site
Task 2: search_news
Task 3: query_database
Task 4: read_knowledge_base
   ↓  Fan-in → 汇总 → 下一个 Step
v2.0 写"一个 Step produces 一个 Task"——对第一版好理解，但把架构限制死了。一对多才能支持 Parallel / Planner / Multi-Agent / Workflow / Fan-out / Fan-in。

Execution Domain：Business vs Kernel

Business                              Kernel
─────────────────────────────────    ──────────────────────────
AgentRun                              Task
WorkflowRun                             │
SkillRun                                ↓
EvaluationRun                        Execution
     │                                  └── Attempt
     │ 内部产生可执行工作
     └──────────────────────────────→ Checkpoint / Lease / Cancellation
✗ v2.0：Kernel Execution = TaskExecution / ToolExecution —— 新套娃。会被追问"Execution 是抽象还是实体？""ToolExecution 是 Task 还是 Execution？"
✓ v2.1：删除这两个领域对象。Kernel 只有 Task / Execution / Attempt。
唯一链路：ToolCall → Action → Task(type=TOOL) → Execution → Attempt。一个 Tool Call 产生 Task，不直接产生 ToolExecution。
✗ 含糊："AgentRun 是业务级执行实例" —— 没回答"AgentRun 自己是不是也由 Kernel 管？"
✓ v2.1：AgentRun 是业务语义上的 Run，不等价于 Kernel Execution；但 AgentRun 内部产生的可执行工作（Task）由 Kernel 管理。 否则将来做 WorkflowRun / SkillRun / EvaluationRun 时会再次出现"到底谁才是 Execution"。

3 · 状态机（P1 升级：SUSPENDED + Reason）

CREATED ──► QUEUED ──► RUNNING ⇄ SUSPENDED ──► COMPLETED
                          │                  ──► FAILED
                          │                  ──► CANCELLED
                          └──► (retry → 开新 Attempt)
为什么去掉 WAITING_HUMAN 顶层状态？
WAITING_HUMAN 不是生命周期状态，它描述的是"为什么当前 Execution 没有继续执行"—— 属于 SuspensionReason。
{ "status": "SUSPENDED",
  "suspension_reason": "HUMAN_APPROVAL" }
以后新增等待类型 无需增加顶层状态。
suspension_reason 取值
  • HUMAN_APPROVAL — 人工审批。Checkpoint 后释放 Worker，数小时后 Event 唤醒 Resume
  • CHILD_AGENT — 等待子 Agent 返回
  • TIMER — 定时唤醒 / 延迟执行
  • EXTERNAL_EVENT — 等待外部系统回调
TIMEOUT 也不再是顶层状态 —— 它是 Attempt 层的失败原因，映射到 FAILED。

4 · Core Domain Contracts（P1 重命名）

⚠️ v1 称"五大核心协议"不严谨。Goal / State / Decision / Action / Observation 是领域契约；真正的 Protocol 应是 Execution Protocol / Event Protocol / Tool Protocol / Agent Protocol / Model Protocol。
① Intelligence Contracts
  • Goal — 可执行任务定义（≠ UserRequest）
  • State — 当前知道什么 + 执行到哪
  • Decision — 下一步判断，不直接执行
  • Action — 具体意图
  • Observation — 感知世界的统一接口
  • Plan — 执行图（DAG）
② Execution Contracts
  • Task
  • Execution
  • Attempt
  • Checkpoint
  • Lease
  • Cancellation
③ Integration Contracts
  • Tool
  • Skill
  • Agent
  • Model
  • Event
Goal→ Decision→ Action→ Task→ Execution→ Observation→ State→ Decision …
Action 取值：ToolCall / SkillCall / AgentDelegation / HumanApproval / AskUser / Finish
⚠️ Decision 的 Confidence 不要用成概率。{"action":"send_email","confidence":0.97} 不意味着决策 97% 正确 —— LLM confidence 不是 calibrated probability。
字段改名 confidence_signal 或归入 decision_metadata。禁止 confidence > 0.9 → 自动执行；是否自动执行由 Policy / Guardrail / 风险分级决定。

5 · 数据底座（P0 表述修正）

✗ v1："PG 保留当前状态，Kafka 保留事件流（Execution Truth）" —— 既然声明不采用纯 Event Sourcing，就不能又说 Kafka 是 Truth，会被面试官抓住
✓ v2：PostgreSQL = Current Durable State / Business Source of Truth；Kafka = Durable Event Log / Event Backbone。
PG + Kafka 通过 Transactional Outbox + Idempotent Consumer 保证状态变化和事件传播的一致性。

7 · Event / Observation / State / Trace 彻底区分

概念定义例子
ObservationAgent 感知到的东西Tool 返回的结果
Event系统发生过的事情ToolExecutionStarted / ToolExecutionCompleted
State系统当前状态run.status = RUNNING
Trace执行链路（观测视图）OTel Span Tree
Event→ Event→ Event→ Observation→ State Change
Observation 是给 Agent 看的；Event 是给 系统 / 审计 / 评估 看的。不要混。

Observation 不直接更新 State（需要 State Reducer）

Execution Result
      ↓
Observation Processor
      ↓
Observation                ← 事实："balance = 100"
      ↓
State Transition (Reducer) ← 解释：写入 variables / 更新 completed_tasks
      ↓
New State                  ← "account_balance = 100"
Observation 是事实/感知（append-only，不可变）；State 是系统解释后的当前状态（可变，带 version）。State.apply(observation) 内部就是 Reducer —— 唯一的合法状态变更入口。

8 · Execution Kernel 全貌

九大能力 —— 六个最易被混成"失败重试系统"，必须一句话说清

Attempt
我试了一次
失败开新 Attempt，保留失败证据。Retry ≠ 状态回退
Retry
我要不要再试
Exponential Backoff + Error Classification
Recovery
系统怎么从异常状态恢复
Lease 过期扫描 / Attempt 重建（见下方两层区分）
Checkpoint
从哪里继续
崩溃从最近点恢复（见下方恢复边界）
Lease
谁现在拥有执行权
租约 + Heartbeat；禁止 RUNNING → QUEUED
Idempotency
重试后会不会重复副作用
At-Least-Once + 幂等键。Retry ≠ Safe
State Machine
通用机制（见下）；原子 Domain Operation + Optimistic Lock
Scheduler
只认 Task；Atomic Claim；Priority + Aging 防饥饿
Cancellation
生命周期管理属 Kernel（见下）

StateMachine 是通用机制，不是 AgentRun 专属（v2.1）

StateMachine（通用 Kernel Mechanism）
├── AgentRunStateMachine
├── TaskStateMachine
├── ExecutionStateMachine     ← 第一版实现
├── AttemptStateMachine       ← 第一版实现
└── WorkflowRunStateMachine   （未来）
v2.0 说"是 Kernel 能力"，但展开的全是 AgentRun 状态机 —— 会被追问"到底是 AgentRun 的还是通用的？"。第一版只实现 Execution + Attempt，AgentRun 状态由它们派生。

Recovery 分两层（消除 Harness / Kernel 撞车）

Execution Recovery（Kernel）Agent Recovery（Harness）
解决什么Worker crash / Lease expired / Attempt failed / Execution stale / Checkpoint resumeTool failed / Need replan / Change model / Ask human / Change strategy
一句话怎么把 Execution 救回来Agent 失败以后下一步怎么办
层级基础设施级业务策略级
命名Recovery改名 AgentRecoveryStrategy（避免两个 RecoveryManager）

Cancellation 归属

User / Policy / System
        ↓
Cancellation Request          ← Harness 可以发起请求
        ↓
Kernel Cancellation           ← 生命周期管理属于 Kernel
        ↓
Worker CancellationToken
        ↓
Execution terminated
不存在"Harness 的 Cancellation 和 Kernel 的是两个东西"的问题。

SUSPENDED 的 Wake-up 机制（v2.1 补齐，否则闭环不完整）

Suspended Execution
        ↓
Wait Condition  (HUMAN_APPROVAL / CHILD_AGENT / TIMER / EXTERNAL_EVENT)
        ↓
Event / Timer 到达
        ↓
Wake-up                    ← Kernel 的 Resume 机制
        ↓
Runnable Task              ← 重新变成可调度单元
        ↓
Scheduler
        ↓
继续执行（用 Checkpoint 恢复）
Wake-up 属于 Kernel，不是 Harness。这样 Actor + Mailbox、Event 唤醒 Resume 才真正落到执行模型上。

Checkpoint 的恢复边界（防止退化成大 JSON）

Checkpoint
├── current_step          执行到哪一步
├── completed_tasks       已完成的任务
├── execution_state       执行状态
├── context_snapshot_id   ← 只存 ID 引用，不内嵌
├── variables             变量
├── artifacts             产物引用
└── recovery_metadata     恢复所需元信息
ContextSnapshot = 模型上下文是什么；Checkpoint = 执行到哪里了 + 恢复需要什么（引用而非内嵌）。

两种执行模型（Actor 已降级，不进第一版核心）

Execution Kernel
├── Task Execution        无状态 / 短任务：claim → run → done   ← 执行模式，非领域实体
└── Stateful Execution    长任务
      └── Actor + Mailbox

Mailbox 消息：UserMessage / ToolResult / ApprovalResult /
             ChildAgentResult / TimerEvent / ExternalEvent / Cancellation
Kernel 里不再有 TaskExecution / ToolExecution 领域对象；上图"Task Execution"是执行模式描述。领域实体只有 Task / Execution / Attempt。

第一件事不是 FastAPI，也不是 Kafka。
先把这 8 个核心对象的领域模型和不变量定义出来 —— 这一步做好，后面的 PG 表、API、Worker、Kafka 都会自然长出来。
Intelligence（5）
Goal · State · Decision · Action · Observation
Execution（3）
Task · Execution · Attempt

✓ v2.1：Domain → StateMachine → Kernel → Repository Interfaces → PostgreSQL → Redis/Kafka
